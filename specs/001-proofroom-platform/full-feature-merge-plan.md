# ProofRoom 原版全功能与本地改造合并方案

版本：1.0，2026-11-15。状态：六项主要冲突已由用户确认；新增套餐与手工配额冲突 D07 待确认。完整方案待整体评审，尚未授权实施。

本轮只做源码、文档及会话核对，编写方案，不修改程序、配置、数据库、原型或测试，不启动/停止服务，不提交或推送。本文件及交接说明属于文档。回答冲突问题不等于授权开始开发。

## 1. 合并目标与基线

目标是保留 GitHub 原版已有功能，加上 11 月 14～15 日本会话要求的改造能力。保留意味着页面入口、业务操作、权限、数据与异常恢复都有对应实现；把源码放在 `upstream/` 中不算功能已接入。

| 基线 | 核对范围与用途 |
|---|---|
| GitHub 原版 | `meilechb/proofroom@eff48d0e45dbc8b355c1d4e2d4cf4a2045eb87e8`；与 18332 原版预览一致，本项目 `upstream/` 保存源码 |
| 当前改造版 | `agent/proofroom-local-main@a3873eb`，业务提交 `27cb7b3`；`apps/web`、`apps/api`、`apps/worker`、`packages/*` |

| 原型 | `docs/prototypes/public-booking-v1/` 是独立评审稿，不是已替换的正式客户页，也不代替原版网站、商城或平台后台 |

原版源码盘点包含 **109 个 page.tsx、50 个 route.ts、28 个测试文件和 7 个 Lightroom Lua 文件**。这些是检查索引，不是 109 项业务已重新验收的证明。完整路由索引附在文末，实施时须逐项核销，不能仅按主菜单判断覆盖。

原版文档存在历史口径差异：`ARCHITECTURE.md` 仍有旧 $40 单档订阅描述，`BUILD-PLAN.md` 也有早期取消分档的文字；当前基线的 `src/lib/plans.ts`、`PRICING-PLAN.md` 已是 Free/Pro。商店计划中的“全部概念”包含未完成或已取消事项。采用实际源码、实际路由和后续明确决策，不把旧文档的每条设想当成已经交付的功能。

### 1.1 本次明确修订的范围

旧需求 §1.3 和 §13 曾把支付、商城、营销、额外插件等排除在本期之外。用户现在要求原版全功能保留，因此这些 **原版已有模块重新成为必保范围**。不能继续用旧排除条款删掉它们，也不能把“PicPeak 扩展不做”解释成“ProofRoom 同类功能可删除”。

新增微信支付、支付宝、实体冲印对接、AI 修图、原生 App、全新岗位权限等不因本次合并自动加入。原版未落地的规划另列，不伪装成“恢复原有功能”。

## 2. 用户已确认的六项合并决策

| 编号 | 冲突 | 已确认的最终口径 |
|---|---|---|
| D01 | 原版直接预约建单/占档与改造版咨询意向不占档 | **默认摄影师确认后占档；保留可选的原版即约模式**。两个模式共享真实占用数据，同一服务当前采用哪个模式必须明确 |
| D02 | 原版付费图库/商店下载门禁与拍摄项目 30 天不限次 | **拍摄交付、收费图库、商店分别保留各自规则**。不得把某一场景的规则套到全站 |
| D03 | 原版与改造版界面差异 | **平台后台以原版为主；摄影师、老板、客户以最近两天改造为主，原版功能全部保留**。不是所有页面统一退回原版，也不是继续用新版少量页面代替原版模块 |
| D04 | 原版加片自动算费与改造版超选线下沟通 | **默认线下确认；套餐/项目可选自动计费**。自动计算费用不等于未经客户确认自动扣款 |

| D06 | 原版 Free/Pro 收费与此前本地免费开发口径 | **按照原版收费逻辑**。不默认赠送 Pro，不默认豁免本地工作室，不把真实收费功能降成仅有入口的演示 |
| D07 | 原版 Pro 不限存储/Free限制与新增平台手工配额 | **待用户确认**。已提出按原版权益保默认、保留管理员显式安全限额的方案；不得自行把旧默认额度变成 Pro 商业限制，也不得擅自删除新增配额功能 |

D07 裁决前，G2/G3 不得固化套餐/配额字段映射。原版 Pro 的 null=不限不能自动变成当前默认 quota_bytes；Free 降级后用量高于5GB时仍须保旧内容并限制新增，不能被现有“新额度不得低于当前用量/预留”的后台变更校验拒绝降级。商业权益与管理员显式安全上限须分清。

其余规则通过分场景、保留原入口和兼容数据解决，不擅自削减任何一方功能。实施时若发现新冲突，建立新的决策项，写清原行为、改造要求、影响和选项，暂停该冲突相关步骤，向用户确认后再做；不自行选择“最简单”的删减方案。

### 2.1 D06 的原版收费口径

依据当前基线源码，而非旧架构文档：

- Free：1 个席位、5GB 存储，保留原版对应基础能力。
- Pro：每席每月 18 美元，保留原版权益；新工作室完整 Pro 试用 14 天。
- 未订阅且试用到期按原版降为 Free；不因为试用结束直接删除业务数据。
- Free 超额时，已有内容保持可访问/下载，限制新增上传；多余成员按原版权益限制，不删除成员记录。
- 续订、取消、欠费、补偿权益、席位数量同步、账单门户和转介绍奖励保持原版业务规则；平台暂停仍是独立的强制状态。
- 原版取消、删除、保留期限等源码与旧注释不一致时，按实际有效路径核对，不能仅凭 `RETENTION_DAYS` 常量就启动数据清理。
- 金额币种保留原值，不把 $18 自动改成 ¥18；拍摄套餐可以保留人民币文字及结构化人民币金额，两者与平台订阅价格是不同业务。
- 现有改造库缺失的订阅/试用字段，迁移前先出账号与权益影响清单；不得擅自重置试用期、赠送权益或将用户直接置为付费。正式调用支付机构和切换真实账单另行执行，不在本轮发生。

## 3. 角色、数据与功能保留原则

业务使用者仍是平台方、工作室、客户三类。权限身份为平台管理员及工作室 Owner/Admin/Member，加客户访问上下文；同一账号可以兼任平台管理员和某工作室成员。“老板”对应 Owner，不再另造一套重复账号。商店买家属于客户场景，不能继承工作人员权限。

所有模块必须按工作室隔离。平台支持保留原版只读代看，并叠加改造版的审计、来源校验、即时撤权和账号安全。没有配置、没有权限、未读取成功和真实空数据必须区分显示。

去重只针对重复入口或同一业务的重复录入，不针对业务能力：

- “素材库”“公开作品”“客户图库”用途不同，不能因为都显示图片就删除一个。
- “咨询”“客户”“拍摄项目”“商品订单”用途不同，不能合并成一张只有姓名的列表。
- “付款状态”“拍摄进度”“选片交付阶段”“预约状态”“合同状态”不能互相覆盖。
- “拍摄选片”“售前参考”“商店收藏”含义不同，不能共用一个布尔值。
- 一个事实只保存一份：项目从咨询确认生成，不重复录入问卷；套餐、时间和参考选择在摘要与表单间同步。

## 6. 合并后的页面与使用流程

### 6.1 平台管理员

以原版 `/admin` 的工作室管理、详情、指标、线索、邮件、转介绍和设置为主。接入当前 API、审计和安全能力。现有 `/studio/platform` 保兼容入口，可跳到正确的管理页；不产生两套平台后台数据，也不把“只读代看”改成可随意代改客户资料。

### 6.2 摄影师、老板与团队

以最近改造的常驻外壳和任务流程为主。桌面侧栏提供分组入口，工作台保今日安排/待办直达；手机保工作台、项目、新建、咨询、我的五个主入口。

恢复的客户 CRM、任务、日历、图库、素材/公开作品、网站编辑、商店、邮件、导入、Lightroom、订阅/转介绍等放入清楚分组；手机在“我的”或对应业务上下文可达，不能删功能，也不把十八个旧导航项塞到一个底部 tab 栏。角色与付费限制按原版控制，受限时显示原因和升级入口，而非凭空消失或伪装成空列表。

“项目”继续承载一单拍摄的核心操作。图库入口保独立图库和团体事件，客户入口保跨项目客户档案。老板不是另一套重复工作台，只是在同一工作台获得 Owner 权限。

### 6.4 主流程与状态

默认拍摄单：公开表达 → 摄影师确认/手工建单 → 占档并冻结本单约定 → 原片批次就绪 → 客户选片并提交 → 精修对应齐套 → 交付/下载 → 到期、续期或历史找回。

即约单使用原版占位/建单流程，后续仍进入同一个项目/照片体系。付费图库与商店各有收费和授权条件，不能用一笔商店付款把拍摄项目直接推进 P4。

## 7. 技术合并方案

继续采用现有工作区，不新建第三套业务系统，不换语言、前端框架或 PostgreSQL。

| 层次 | 职责 |
|---|---|
| `apps/web` | 原版平台后台组件 + 最近改造的工作人员/客户外壳；接回原版业务页面与网站/商城；只通过契约请求业务数据 |
| `apps/api` | 唯一业务 JSON API、身份与租户校验、公开/私密客户入口、插件协议兼容、支付和邮件回调、受控媒体网关 |
| `packages/domain` | 原版完整业务与当前工作流的统一规则，费用/授权/快照/版本/幂等逻辑 |
| `packages/contracts` | 前后端共享 schema、DTO、错误码、分页/游标、状态和插件版本合同，不依赖服务端凭据 |
| `packages/db` | 普通 PostgreSQL、连接池/单连接事务、增量迁移、约束/索引和租户所有权 |
| `apps/worker` | 图片/ZIP、导入、邮件、自动化、到期处理、计量与清理；持久任务、幂等、限流和可观察恢复 |
| 外部适配 | 对象存储、Stripe/Connect、Resend/发送域、Google OAuth、域名托管等保留可替换适配；前端不携带密钥 |

原版页面尽量复用其已有业务组件，接入新外壳及 API，不再次从零重写一套功能缩水的页面。原版 `db()`/Neon/`server-only`/Server Actions/Blob/host 查询耦合逐项移到 API/domain/worker；不能让原版页继续连旧库、其余页连新库，再把两个站点相互链接称作合并。

对象存储保留原公有素材/私有图库的隔离语义，走现有 S3 兼容目标与媒体网关。保留缓存/ETag、Range、HEAD、下载中即时撤权等要求。原图保持源字节，公开预览去除不应公开的元数据，授权的内部拍摄时间排序仍保留。统一上传按图片、数字商品和文档分类型；只有图片生成图片变体，不能把预设包/电子书/合同全部送入图片处理器或用原片的格式白名单误拒。支付和邮件回调保签名校验、事件去重、退款撤权和重放安全。

正常业务导航继续 Next 客户端路由，不要求必须使用 hash。OAuth 登录仍遵守现有账号禁用、MFA与强制改密保护，不借第三方登录绕过。OAuth/支付外站返回必须验证 state/return URL、重读真实结果、恢复原页面；不把浏览器返回或关闭支付页当作成功/失败凭证。

### 7.1 数据模型的兼容方式

- 扩展统一的 clients，容纳原邮箱/公司/电话与新微信/称呼；新咨询不强制邮箱，邮件/支付等确需邮箱的动作在当时补充。重复邮箱、共享家庭联系方式等先展示冲突，不擅自合并客户。
- 原订单与新项目建立明确对应，一份主记录及不同状态维度。新增字段不丢弃原金额、币种、编号、签约、付款、计划或原需求快照。
- 图库保留普通、团体父子、项目托管等用途。新拍摄项目默认原片/精修两组，不意味着数据库全局只能有两种图库或只能建两本。
- 用明确用途区分精修清单、售前参考、商店收藏和工作人员标记。原版插件继续获取兼容的 client favorite/评论，新星色信息使用明确的协议扩展，不擅自改变旧插件 1/0 feedback 的含义。
- 文件采用稳定 ID 与修订/对象引用，图库之间可以复用媒体；引用复制不重复占用整份存储，也不因某处移除就删掉别处仍需的源文件。
- 已交付版本不可被后台覆盖。按 D05 将重发源、处理变体、清单与对应关系组成待确认修订；旧下载指向旧交付清单，确认新修订才发布新集合。
- 商业商品的分辨率/授权文件、拍摄源文件和网页预览是不同交付类型，有明确名称、摘要及授权，不混用。
- 订阅/权益、支付、礼品卡/折扣使用服务端事实及事务控制；保原币种和金额精度，不从“¥1280左右”之类报价文字强行解析成账单。

### 7.2 三种下载策略

| 场景 | 可下载条件 | 期限/次数与内容 |
|---|---|---|
| 拍摄项目交付 | 通过完整批次/清单/对应条件进入交付；用户有项目权限 | 首次交付起 30 天、不限次数；续期和补片规则保留；源文件单图及全部/原片/精修 ZIP |
| 普通收费图库 | 按原图库发布、到期、下载开关、访问/下载码，以及配置的付款门禁 | 保原可配置期限和原图/网页尺寸选项；不因属于同工作室就绕过门禁 |
| 商店订单 | 确认有效付款或原手动付款流程，并有有效购买授权 | 保原商品授权/期限/次数/分辨率/许可证；默认授权配置取原版实际字段，退款/争议按原规则撤销 |

`archived` 在原版普通图库可能表示关闭，在新版项目历史不必表示到期禁止下载，因此不能按同名字段机械互拷。由具体资源用途和授权策略判断。
